# 信息中枢 · 证据链实现说明（第一层：数据深度）

> 版本：v1.0 ｜ 日期：2026-09-25
> 目标：把「双非友好」从一句口头标签，变成**可点击、可核对、可审核**的证据链。
> 结论一句话：**没有原文摘录，就没有「双非友好」。**

---

## 一、这一层解决什么问题

改造前的问题（已核实）：

| 问题 | 位置 | 后果 |
|---|---|---|
| 岗位库 24 条全是匿名占位（「杭州某电商 SaaS 独角兽」），0 家具名公司 | `apps/web/src/lib/jobs-data.json` | 用户与评委无法核对，说服力为负 |
| 投递链接指向 BOSS/实习僧**搜索页**，不是具体岗位 | 同上 | 点开即穿帮 |
| 「双非友好」是手写布尔值，无任何依据 | `jobsData.jobs[].firstDegreeFriendly` | 无法自证，评委一问即倒 |
| 联网检索是 `demoSearch()` 假结果 | `apps/web/src/lib/infobase.ts` | 假信息来源违反自己的合规红线 |
| 信息差 Skill 让模型自行编造公司与链接 | `packages/llm/index.ts` → `buildInfoPrompt` | 模型幻觉直接变成「机会」 |

改造后的规则：

1. 证据必须有**原文摘录（≥8 字）+ 可点击来源（http/https）**，否则不产出证据；
2. 「双非友好」标签**不由模型断言、不由数据字段存储**，一律由 `deriveFriendlyLevel()` 计算；
3. 只有「白名单官方来源 + 强信号 + 正向」自动通过，其余进人工审核队列；
4. 检索未配置 Key 时**返回空结果并说明原因**，绝不返回示例/伪造结果。

## 二、三级标签（避免过度断言）

| 标签 | 条件 | 含义 |
|---|---|---|
| **双非友好 · 有据** | 有「已通过 + 正向 + 强信号」证据 | 有原文依据支撑「对双非友好」的结论 |
| **门槛可及** | 仅有 `degree_barrier` 证据（如「本科及以上」） | 只能说门槛够得着，**不能**推出「不限院校」 |
| **未见依据** | 无可用证据 | 不给任何暗示 |

外加独立的风险位：**含限制性表述**（`direction = 'negative'`，如「仅限 985/211」「第一学历」），出现即提示，且永远不会点亮友好标签。

强信号 = `policy`（政策依据）/ `bonus`（不限专业等）/ `school_list`（不限院校等）/ `historical_admit`（录取公示）。
弱信号 = `degree_barrier`（学历门槛）/ `deadline`（时间窗口）。

## 三、数据结构

共享契约：`packages/types/index.ts`
- `evidenceItemSchema`：id / company / role / signal / direction / quote / sourceUrl / sourceSite / publishedAt / fetchedAt / credibility / reviewer / status
- `hubJobSchema`：岗位 + `evidence[]`（**没有** `firstDegreeFriendly` 字段）
- `contributionSchema` + `CONTRIBUTION_TRANSITIONS`：审核状态机
- `deriveFriendlyLevel()` / `hasRestrictionEvidence()`：标签门禁
- `contributionToEvidence()`：只有「已通过 + 有摘录 + 合法链接」的贡献才能转成证据

数据库：`supabase/migrations/007_evidence_hub.sql`

| 表 | 作用 | 关键约束 |
|---|---|---|
| `evidence_items` | 证据条目 | `quote` ≥8 字、`source_url` 必须 http(s) |
| `hub_jobs` | 岗位（去匿名化） | `url` 必须 http(s) |
| `hub_contributions` | UGC 投稿与审核 | **`status='approved'` 必须有 ≥8 字原文摘录** |
| `hub_points_ledger` | 贡献积分流水 | 审核通过时按可信度记分 |
| `hub_whitelist_domains` | 可运营配置白名单 | 不改代码即可扩域名 |

状态机（数据库触发器 + 前端共用同一张表）：
```
pending     → approved | rejected | needs_info
needs_info  → pending  | rejected
rejected    → pending
approved    → （终态）
```

可信度分级与积分：`A 官方原文 = 30 分`、`B 权威来源 = 20 分`、`C 用户投稿 = 10 分`。

## 四、检索与白名单

- 适配层：`apps/web/src/lib/search-provider.ts`，已实现**博查 AI Web Search**（需求书 §4.2 方案 B）。
- 白名单：`apps/web/src/lib/whitelist.json`，**38 个域名**，与采集脚本共用同一份数据。
  - `official`（可信度 A）：政府/公共就业（gov.cn、ncss.cn、job.mohrss.gov.cn…）、企业官方校招站（join.qq.com、campus.alibaba.com…）、高校就业网（job.hdu.edu.cn、job.zjut.edu.cn…）
  - `authoritative`（可信度 B）：牛客、实习僧、应届生、智联、BOSS、猎聘、前程无忧、拉勾、脉脉
  - 非白名单 → 可信度 C，只能作线索，**不能作证据**
- 复核命令：`npm run hub:verify-whitelist`（加 `--write` 写回实测结果）
  - 现状：25 个实测可达（200/403/412），13 个标记 `unverified` 待再核（本机代理可能误报 502）。

环境变量（`apps/web/.env.local`）：
```
BOCHA_API_KEY=            # 不配则联网检索降级，但不返回任何假结果
HUB_SEARCH_ENDPOINT=      # 可选，默认 https://api.bochaai.com/v1/web-search
HUB_WHITELIST_EXTRA=      # 可选，逗号分隔追加域名
```

## 五、采集脚本

```bash
# 单次检索并抽取候选证据（输出到 data/hub-harvest-YYYY-MM-DD.json）

# 直接推送进 Supabase（需要 SUPABASE_URL + SUPABASE_SERVICE_ROLE_KEY）
```

脚本不会绕过门禁：摘不到原句的结果直接丢弃；非白名单域名不产出证据；只有 official + 强信号 + 正向才自动 `approved`，其余一律 `pending` 等人审。

## 六、当前数据（2026-09-25 实采）

| 项目 | 数量 | 说明 |
|---|---|---|
| **岗位/公告** | **39 条**（全部 2026 年，最新 2 天内） | 全部来自官方来源 + 带原文证据 + 按发布时间倒序；7 天内的显示「最新」标记 |
| **证据条目** | **130 条** | 128 已核实 + 2 待审核；覆盖 **45 个来源站点** |
| 政策类证据 | 15 条 | 国务院政策文件库（gov.cn）官方原文，含 2026 年两份「十五五」规划 |
| 来源导航 | 14 个 | 政府 / 企业官方校招站 / 权威平台入口 |
| 白名单 | 38 个显式域名 + 2 条域名空间规则 | 规则见下 |

采集消耗：5 批共 **148 个检索词**（约 148 次博查调用）。

### 6.1 关键经验：白名单不能靠逐个枚举

第一轮采集（28 个检索词）白名单命中率只有 **2/20** —— 因为博查返回的正是各高校就业网的真实岗位，
而白名单里只列了 2 个高校域名。逐个枚举全国高校域名不可行。

解法是把白名单从「枚举」升级为「域名空间规则」：

| 规则 | 覆盖 | 可信度 |
|---|---|---|
| `gov.cn` 全站 | 各级政府机关（含人社、公共招聘） | A |
| `edu.cn` + `job./career./jyb./jy./jobinfo./employment./jiuye./zhaopin./zhiye.` 前缀 | 全国高校官方就业服务子站 | A |

依据：`gov.cn` 与 `edu.cn` 都属于「注册即有资质审核」的受限域名空间，因此不需要逐个人工核验。
改用规则后，单次采集从 0 条提升到 5 条证据 + 5 个岗位，最终累计到 112 条岗位。

### 6.2 岗位库准入的三条硬规则

1. **只收官方来源**（高校就业网 / 政府 / 企业官方校招站）——招聘平台的列表页不是岗位；
2. **必须能解析出真实企业名**——「某平台」不是雇主；企业名优先从标题解析，失败则从职位正文提取「XX有限公司」；
3. **标题不能是列表页/过滤页**——过滤掉「职位&公司对比」「招聘信息-」这类页面。

这三条把第一轮 92 条「岗位」砍到 23 条，但砍掉的全是重复转载、平台列表页和匿名条目。

### 6.3 跨来源去重

同一份 JD 常被多所高校就业网转载（同一岗位最多见到 4 个学校页面）。去重按两层：
先按**原文摘录**去重（同一份 JD 文本相同），再按**企业 + 岗位**去重；
同组重复时优先保留**能解析出真实企业名**的那一条。

```bash

node scripts/harvest-evidence.mjs --preset --preset-file scripts/harvest-preset-4.txt --deep --merge
node scripts/harvest-evidence.mjs --preset --preset-file scripts/harvest-preset-5.txt --deep --merge
```

参数说明：

| 参数 | 作用 |
|---|---|
| `--preset` | 使用 `scripts/harvest-preset.txt` |
| `--preset-file <path>` | 使用指定检索词文件（一行一个，`#` 为注释） |

## 八、继续扩量的建议

- **换批次重新跑**：检索词重复时结果也会重复（脚本会去重），要增量必须换城市/岗位/行业/年份组合；

## 九、时效性：让岗位「实时最新」

### 9.1 踩过的坑

第一轮采集用了 `freshness: 'noLimit'`，结果**混进大量 2023–2024 年的旧公告**：

\`\`\`
清理前 112 条岗位的发布年份分布：
  2023 年：17 条      2024 年：36 条      2025 年：43 条      2026 年：20 条
  → 其中 16 条页面明确标注「已过期」
\`\`\`

一个满是过期岗位的「岗位库」，对用户是负价值。

### 9.2 修复

| 措施 | 说明 |
|---|---|
| **采集时效参数** | `HUB_SEARCH_FRESHNESS` 默认改为 `oneYear`，实时批次用 `oneMonth`；可选 `oneDay/oneWeek/oneMonth/oneYear/noLimit` |
| **清理脚本** | `scripts/prune-stale-jobs.mjs`：移除「页面标注已过期」与「证据年份早于去年」的岗位 |
| **前端体现时效** | 岗位默认**按发布时间倒序**；卡片显示发布日期；7 天内的打「最新」标记；陈旧/过期打琥珀色标记 |
| **自动刷新** | `.github/workflows/refresh-hub.yml`：每周一自动重新采集（默认 `oneWeek`）+ 采集政策 + 清理过期 + 跑门禁 + 提交 |

### 9.3 实测验证

\`\`\`
freshness=oneMonth 检索「杭州 软件开发 校园招聘 公告」：
  返回 10 条，日期全部为 2026-08 ~ 2026-09（当天 2026-09-26）
  → 时效参数确实生效

重采后岗位库：
  39 条，证据年份分布 {2026: 39}，最新一条 2026-09-24（2 天前）
\`\`\`

### 9.4 注意：时效与「白名单」的张力

最新招聘信息大量出现在**中公、华图、银行招聘网**等培训机构/聚合站上（实测官方源占 3–4/10）。
本项目的处理方式是**不放松白名单**：
- 官方源（edu.cn / gov.cn）→ A 级，自动通过，可进岗位库；
- 聚合站（若在显式名单内）→ B 级，只进证据审核队列，不自动进岗位库。

代价是最新岗位数量增长较慢，收益是**每一条岗位都能点开官方原文核对**。

## 十、成本与计费（重要）

### 9.1 谁在花钱

| 入口 | 是否消耗博查余额 | 说明 |
|---|---|---|
| 浏览证据库 / 岗位库 / 来源导航 | **不消耗** | 读静态 `hub-seed.json`，与 API 无关 |
| `/api/hub/search`（页面上的「联网检索」） | **消耗**，每次检索 1 次调用 | **唯一**对用户开放的花钱入口 |
| `scripts/harvest-*.mjs`（采集脚本） | 消耗，但**一次性** | 只有运营侧手动运行才花钱 |
| AI 技能（简历/面试/匹配等） | 消耗 **DeepSeek** 余额 | 另一个 Key，另一笔账 |

**余额耗尽的后果**：联网检索失效并给出明确提示，**但 112 条岗位与 130 条证据照常可访问**（降级不中断）。

### 9.2 三层成本护栏

`/api/hub/search` 绝不能裸奔（否则一个爬虫就能把余额刷空）。护栏见 `apps/web/src/lib/hub-search-guard.ts`：

| 护栏 | 作用 | 环境变量 |
|---|---|---|
| **结果缓存** | 相同检索词在缓存期内命中缓存，**不产生新调用、不扣额度** | `HUB_SEARCH_CACHE_HOURS=24` |
| **每 IP 每日配额** | 限制真实 API 调用次数，超出返回 429 | `HUB_SEARCH_DAILY_LIMIT=3` |
| **总开关** | 对用户关闭检索，只保留已核实库（最省钱） | `HUB_USER_SEARCH=off\|limited\|unlimited`（默认 `limited`） |

实测结果（limit=3）：

```
1) 首次检索   : ok=True  剩余 2/3  累计调用 1
2) 同词再检索 : 命中缓存  剩余 2/3  累计调用 1   ← 缓存不扣额度
3) 换词检索   : ok=True  剩余 1/3  累计调用 2
4) 第三次真实 : ok=True  剩余 0/3  累计调用 3
5) 超额度检索 : ok=False reason=quota_exceeded  累计调用 3   ← 被拦下
```

### 9.3 推荐部署档位

| 场景 | 建议配置 | 成本 |
|---|---|---|
| **正式对外（推荐）** | `HUB_USER_SEARCH=off`，岗位/证据由运营侧定时跑采集脚本更新 | 每周几元，完全可控 |
| 比赛演示 / 内测 | `HUB_USER_SEARCH=limited` + `HUB_SEARCH_DAILY_LIMIT=3` | 每人每天最多 3 次调用 |
| 内部调试 | `unlimited` | 不建议对公网开放 |

> 这与需求书 §1.3 的定位一致：信息中枢应当是**主动聚合**（运营侧采集入库），而不是把检索成本转嫁给每个用户。

### 9.4 已知局限

- 缓存在**进程内存**中：Vercel 多实例部署时，配额是「每实例近似值」而非全局精确值；生产化需替换为 Upstash Redis / Cloudflare KV（保持 `hub-search-guard.ts` 的函数签名不变）。
- 调用计量（`searchUsage()`）同样只在单进程内累计，用于本地审计，不持久化。
