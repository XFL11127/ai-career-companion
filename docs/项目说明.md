## 1. 项目原理（为什么做 / 做什么）

**产品定位**：面向**双非院校学生**的 AI Copilot 式「学职陪伴」产品，覆盖从能力诊断到简历包装的全链路。

**核心差异（5 点）**：

1. **双非垂直定位** —— 唯一面向双非学生的学职产品，非通用求职工具。
2. **三层记忆** —— L1 会话 / L2 用户画像 / L3 知识，跨会话连贯，非应答式。
3. **五 Skill 闭环** —— 诊断 → 规划 → 练兵 → 信息差 → 成果包装，全链路覆盖。
4. **极致轻量** —— 免登即用、首屏 <200KB、10 秒出结果、数据存浏览器本地。
5. **数据驱动** —— KPI 看板 + skill_events 埋点，竞品无此能力。

**设计原则**：本地优先（IndexedDB/localStorage）、降级不中断（无 Key/无 Supabase/无 Worker 均自动回落）、中文双非语境 prompt。

## 2. 实现流程（一次请求的生命周期）

```
用户在前端 Skill 页面输入
   │
   ▼
useSkill hook (apps/web/src/lib/useSkill.ts)
   ├─ L1 召回：recallTurns() 读 IndexedDB 近期轮次
   ├─ L2 注入：loadProfile() 读 localStorage 用户画像
   └─ L3 检索：searchL3Knowledge() 命中静态知识库
   │  （三段拼成 context/profile 注入 prompt）
   ▼
/api/skill/[...path]/route.ts (Next.js BFF, Node 运行时)
   │  或  Cloudflare Worker /skill/[name] (apps/worker/src/index.ts)
   ▼
packages/llm → streamSkill() (async generator, NDJSON 流)
   ├─ 有 DEEPSEEK_API_KEY → createDeepSeek + streamObject（DeepSeek-V3）
   └─ 无 Key / 调用失败   → stubFor() 确定性兜底（保证链路不中断）
   ▼
前端渐进渲染 (SkillCardView 边生成边画)
   ├─ 结果存 IndexedDB (saveResult)
   ├─ 追加会话轮次 (appendTurn) + 会话历史
   └─ 更新用户画像 (updateFromSkillResult → L2)
   ▼
Worker 端（若走 Worker）：流结束写 skill_events + 诊断雷达 memory 到 Supabase
   └─ Supabase 未配 → 内存兜底（memFallback）
```

**三条降级链（务必理解，改动时勿破坏）**：

- 无 `DEEPSEEK_API_KEY` → 用 `stubFor()` 确定性假数据（前端仍完整可演示）。
- 无 `Supabase` → Worker 退化为进程内 `Map` 内存存储。
- 无 `AI` binding（bge-m3）→ 记忆召回退化为关键词包含匹配。

### 3.4 后端（`apps/worker/src/index.ts`，零框架单文件）

- **`export default { fetch }`** 原生处理器，`Bindings` 类型声明环境变量。
- **路由**：
  - `GET /health` —— 健康检查
  - `/memory` (+ `/api/memory`, `/api/memory/search`) —— `handleMemory()`
  - `POST /api/embed` —— bge-m3 向量（`env.AI.run('@cf/baai/bge-m3')`）
  - `POST /skill/[name]` —— `handleSkill()`（五 Skill）
- **`handleMemory`**：GET 召回（有 embedding 走 `cosine()` 余弦检索，无则关键词回退）；POST 写入（Supabase REST 或内存兜底）；DELETE 删除。
- **`handleSkill`**：`skillInputMap` 校验 → `streamSkill()` 生成 NDJSON 流（边生成边返回）→ 流结束写 `skill_events` + 诊断雷达 `memory` 到 Supabase（一次落库，`.catch` 静默）。
- **降级**：`sbReady()` 判 Supabase；`embed()` 判 `env.AI`；任一缺失自动退化为兜底。

### 3.5 共享契约（`packages/types/index.ts`）

- `profileSchema`（双非学生画像）/ `memoryItemSchema`(三层) / `healthSchema`
- `skillInputMap` / `skillOutputMap` —— Worker 与 Web 共用路由表
- ⚠️ **改这里 = 前后端契约变更**，必须双端同步验证 `type-check`。

### 3.6 LLM 层（`packages/llm/index.ts`）

- `runSkill(name, rawInput, env)` —— `generateObject` + zod 校验 + 失败回落 `stubFor`
- `streamSkill(name, rawInput, env)` —— `async function*` 产出 `{done, data, error}` NDJSON chunk
- `stubFor(name)` —— 五 Skill 确定性假数据（演示/降级兜底）
- `buildDiagnosePrompt/Plan/Practice/Info/Package` —— 中文双非语境 prompt 构造
- `withMemory()` / `withProfile()` —— 注入 L1/L2
- `getApiKey()` —— 跨端取 Key（Worker binding 优先，回退 Node `process.env`）

## 9. 代码提交与阶段性检验机制

**分支纪律**：

- 活跃分支 `基础骨架`；短生命周期功能分支 → PR → 评审 → 合 `基础骨架`。
- `master` 归档，不日常开发。

**提交纪律（重要）**：

- AI **不主动** `git commit` / `git push`，由用户操作；AI 仅提示「测试通过后可提交」。
- 每个阶段目标完成且 `type-check` 通过后，提示用户执行 commit/push，再规划下一步。

**阶段性检验**：

1. **CI**：push 到 `基础骨架` 触发 `ci.yml` 跑 `lint` + `type-check`。
2. **看板移卡**：待办 → 进行中（认领+分支）→ 待审核（PR 合入）→ 完成（验收）。
3. **需求溯源**：PR 用 `Closes #编号` 关联 Issue；Issue 模板强制填「需求来源/优先级/验收标准」。
4. **自动化**：`.github/workflows/project-automation.yml`（PR 合自动移卡，需配 `PROJECT_TOKEN` + `PROJECT_NODE_ID`；或改用 GitHub Projects 内置自动化）。
5. **真相源**：`ROADMAP.md`（迭代循环+backlog）+ `TASKBOARD.md`（三栏看板）。

## 10. 可能的 bug 修复方案及后续维护计划

### 常见 bug 与修复

| 现象            | 根因                        | 修复                                                               |
| ------------- | ------------------------- | ---------------------------------------------------------------- |
| Skill 页面空白/报错 | `DEEPSEEK_API_KEY` 缺失     | 应自动回落 `stubFor`；检查环境变量是否注入（Vercel/Worker secret）                 |
| 记忆不连贯         | L1 IndexedDB 未写入/被清       | 查 `appendTurn`/`recallTurns`；IndexedDB 版本升级逻辑                    |
| 召回结果不准        | bge-m3 未配 → 关键词回退         | 检查 `env.AI` binding；无则属预期降级                                      |
| Supabase 写入失败 | RLS / key 错误              | 查 `sbHeaders` 用 anon 还是 service_role；Worker 自动内存兜底不报错            |
| Vercel 构建失败   | Node runtime 错（须 Dynamic） | 确认 3 路由 `ƒ (Dynamic)`；`DEEPSEEK_API_KEY` 已配                      |
| Worker 部署失败   | 未 `--config` / secret 缺失  | `npx wrangler deploy --config apps/worker/wrangler.toml` + 配 Key |
| 前端缓存陈旧        | IndexedDB 存旧结果            | `loadResult` 命中即展示；清缓存或升 `db.ts` VERSION                         |
| 流式中断          | LLM 限流/网络                 | `streamSkill` try/catch 已回落 stub；查 Key 配额                        |

   ▲                                                            │
   └────────────────────────────────────────────────────────────┘

- **硬任务（本循环）**：缓存层（T-002，Upstash/Redis）、国内域名（T-001，P0）、Moonshot 回退（T-003）、README/部署文档（T-004）。

- **常规维护**：依赖安全更新（npm audit）、看板 backlog 勾销、ROADMAP 循环切换、文档与代码同步。
- **禁止事项（守住）**：不主动提交/推送、不登录云端后台、改动 `packages/types` 必双端 type-check、不破坏三条降级链。

## 11. 日常工作流（全角色）

> 本节点是「人 / AI 每日怎么协作」的操作手册，配合 `ROADMAP.md`（迭代循环）与 `TASKBOARD.md`（看板）使用。AI 启动时会自动读本章（见 §0）。

### 11.1 每日启动（AI 自动，人无需手动读）

| 步骤 | 动作 |
| -- | -- |
| 1 | AI 读 `docs/项目说明.md`（本文件，全局约束） |
| 2 | AI 读 `docs/ROADMAP.md`（当前迭代循环 + backlog 优先级） |
| 3 | AI 读 `docs/TASKBOARD.md`（认领 / 移动卡片，需求溯源） |
| 4 | 用 `Grep` / `Read` 定位具体源码（不整仓扫） |
| 5 | 改完跑 `npm run type-check` → 更新看板卡片 → 提示用户提交 |

> AI 不主动 `git commit` / `git push`、不启动 dev server、不登录任何云端后台（见 §9、§10）。

### 11.2 需求 → 验收闭环

```
需求(Issue 模板) → 队长派发(看板待办) → 成员认领(进行中 + 开功能分支)
   → 开发(npm run type-check 0 报错) → 提 PR(标题含 Closes #编号)
   → 合入 基础骨架(GitHub Projects 自动移「待审核」)
   → 队长功能验收(本机 npm run web 自测) → 卡移「完成」+ Issue close
   → 回到 ROADMAP 下一迭代循环
```

### 11.3 角色动作

**队长（A，统筹 / 基础设施 / 部署）**

1. 读全局（AI 自动完成，无需手动）
2. 需求入口：把「谁在哪次对话提的需求」建成 Issue（用 `.github/ISSUE_TEMPLATE`，强制填需求来源 / 优先级 / 验收标准）→ 自动进 Projects 待办
3. 派发：在 `TASKBOARD.md` 待办列建卡或移动，指定负责人（参照 §7 分工表）
4. 定里程碑：按 `ROADMAP.md` 迭代环决定下一个要赢的里程碑
5. 评审 PR：遵循 §9 分支纪律「短生命周期功能分支 → PR → 评审 → 合 `基础骨架`」
6. 验收：「待审核」卡片由队长 / 评委验收 → 移「完成」
7. 治理硬任务：改默认分支为 `基础骨架`、确保 CI 跑 `基础骨架`（不做则队友仍以为停滞）

**成员（B 前端 / C 后端AI / D 数据测试）**

1. 领任务：在 Projects 或 `TASKBOARD.md` 待办列认领一张卡
2. 移到进行中：把卡剪到「进行中」列，填负责人 + 分支
3. 开功能分支：从 `基础骨架` 切短生命周期分支，不直接在活跃分支改
4. 编码：先读 `项目说明.md` §3 定位源码；守住三条降级链、不破坏 `packages/types` 契约
5. 自检：跑 `npm run type-check` 须 0 报错（见 §8 标准）
6. 提 PR：push 分支 → 开 PR，描述写 `Closes #编号` 关联 Issue；合入 `基础骨架` 后把卡移到「待审核」

### 11.4 看板移卡规则

1. **待办 → 进行中**：成员认领时移动，填负责人 + 功能分支名
2. **进行中 → 待审核**：提 PR 并 `Closes #` 合入 `基础骨架` 后移动（或靠 GitHub Projects 内置自动化）
3. **待审核 → 完成**：队长 / 评委功能验收通过后移动，并 close 对应 Issue
4. **每次移卡必须 `git commit` 进 `基础骨架`**：队友 `pull` 即同步；markdown 看板是 AI 无关的真相源，任何 AI（WorkBuddy / Trae / dumate / Claude）和队友均直接读写

### 11.5 队友如何提需求 / 提问

- **提任务 / Bug**：GitHub 仓库 `Issues` → `New issue` → 选模板（功能 / 任务 或 Bug 反馈）→ 填字段（优先级 / 预估工作量 / 功能描述 / 验收标准 / **需求来源**）→ 提交后自动进 Projects「待办」
- **纯提问（非任务）**：建议在仓库开 **Discussions**（Settings → Features → 勾 Discussions），Issue 只收任务 / Bug，避免噪音
- **换 AI 工具**：Trae / dumate / ChatGPT 等只需一句「先读 `docs/项目说明.md` 当上下文」即可拿到同等全局信息（真相源是 markdown，不锁死 WorkBuddy）
