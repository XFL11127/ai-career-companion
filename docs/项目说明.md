## 1. 项目原理（为什么做 / 做什么）

**产品定位**：面向**双非院校学生**的 AI Copilot 式「学职陪伴」产品，覆盖从能力诊断到简历包装的全链路。

**核心差异（5 点）**：

1. **双非垂直定位** —— 唯一面向双非学生的学职产品，非通用求职工具。
2. **三层记忆** —— L1 会话 / L2 用户画像 / L3 知识，跨会话连贯，非应答式。
3. **五 Skill 闭环** —— 诊断 → 规划 → 练兵 → 信息差 → 成果包装，全链路覆盖。
4. **极致轻量** —— 免登即用、首屏 <200KB、10 秒出结果、数据存浏览器本地。
5. **数据驱动** —— KPI 看板 + skill_events 埋点，竞品无此能力。

**设计原则**：本地优先（IndexedDB/localStorage）、降级不中断（无 Key/无 Supabase/无 Worker 均自动回落）、中文双非语境 prompt。

## 2. 实现流程（一次请求的生命周期）

```
用户在前端 Skill 页面输入
   │
   ▼
useSkill hook (apps/web/src/lib/useSkill.ts)
   ├─ L1 召回：recallTurns() 读 IndexedDB 近期轮次
   ├─ L2 注入：loadProfile() 读 localStorage 用户画像
   └─ L3 检索：searchL3Knowledge() 命中静态知识库
   │  （三段拼成 context/profile 注入 prompt）
   ▼
/api/skill/[...path]/route.ts (Next.js BFF, Node 运行时)
   │  或  Cloudflare Worker /skill/[name] (apps/worker/src/index.ts)
   ▼
packages/llm → streamSkill() (async generator, NDJSON 流)
   ├─ 有 DEEPSEEK_API_KEY → createDeepSeek + streamObject（DeepSeek-V3）
   └─ 无 Key / 调用失败   → stubFor() 确定性兜底（保证链路不中断）
   ▼
前端渐进渲染 (SkillCardView 边生成边画)
   ├─ 结果存 IndexedDB (saveResult)
   ├─ 追加会话轮次 (appendTurn) + 会话历史
   └─ 更新用户画像 (updateFromSkillResult → L2)
   ▼
Worker 端（若走 Worker）：流结束写 skill_events + 诊断雷达 memory 到 Supabase
   └─ Supabase 未配 → 内存兜底（memFallback）
```

**三条降级链（务必理解，改动时勿破坏）**：

- 无 `DEEPSEEK_API_KEY` → 用 `stubFor()` 确定性假数据（前端仍完整可演示）。
- 无 `Supabase` → Worker 退化为进程内 `Map` 内存存储。
- 无 `AI` binding（bge-m3）→ 记忆召回退化为关键词包含匹配。

### 3.4 后端（`apps/worker/src/index.ts`，零框架单文件）

- **`export default { fetch }`** 原生处理器，`Bindings` 类型声明环境变量。
- **路由**：
  - `GET /health` —— 健康检查
  - `/memory` (+ `/api/memory`, `/api/memory/search`) —— `handleMemory()`
  - `POST /api/embed` —— bge-m3 向量（`env.AI.run('@cf/baai/bge-m3')`）
  - `POST /skill/[name]` —— `handleSkill()`（五 Skill）
- **`handleMemory`**：GET 召回（有 embedding 走 `cosine()` 余弦检索，无则关键词回退）；POST 写入（Supabase REST 或内存兜底）；DELETE 删除。
- **`handleSkill`**：`skillInputMap` 校验 → `streamSkill()` 生成 NDJSON 流（边生成边返回）→ 流结束写 `skill_events` + 诊断雷达 `memory` 到 Supabase（一次落库，`.catch` 静默）。
- **降级**：`sbReady()` 判 Supabase；`embed()` 判 `env.AI`；任一缺失自动退化为兜底。

### 3.6 LLM 层（`packages/llm/index.ts`）

- `runSkill(name, rawInput, env)` —— `generateObject` + zod 校验 + 失败回落 `stubFor`

- `buildDiagnosePrompt/Plan/Practice/Info/Package` —— 中文双非语境 prompt 构造
- `withMemory()` / `withProfile()` —— 注入 L1/L2
- `getApiKey()` —— 跨端取 Key（Worker binding 优先，回退 Node `process.env`）

## 9. 代码提交与阶段性检验机制

**分支纪律**：

- 活跃分支 `基础骨架`；短生命周期功能分支 → PR → 评审 → 合 `基础骨架`。
- `master` 归档，不日常开发。

**提交纪律（重要）**：

- AI **不主动** `git commit` / `git push`，由用户操作；AI 仅提示「测试通过后可提交」。
- 每个阶段目标完成且 `type-check` 通过后，提示用户执行 commit/push，再规划下一步。

**阶段性检验**：

1. **CI**：push 到 `基础骨架` 触发 `ci.yml` 跑 `lint` + `type-check`。
2. **看板移卡**：待办 → 进行中（认领+分支）→ 待审核（PR 合入）→ 完成（验收）。
3. **需求溯源**：PR 用 `Closes #编号` 关联 Issue；Issue 模板强制填「需求来源/优先级/验收标准」。
4. **自动化**：`.github/workflows/project-automation.yml`（PR 合自动移卡，需配 `PROJECT_TOKEN` + `PROJECT_NODE_ID`；或改用 GitHub Projects 内置自动化）。
5. **真相源**：`ROADMAP.md`（迭代循环+backlog）+ `TASKBOARD.md`（三栏看板）。

## 10. 可能的 bug 修复方案及后续维护计划

### 常见 bug 与修复

| 现象            | 根因                        | 修复                                                               |
| ------------- | ------------------------- | ---------------------------------------------------------------- |
| Skill 页面空白/报错 | `DEEPSEEK_API_KEY` 缺失     | 应自动回落 `stubFor`；检查环境变量是否注入（Vercel/Worker secret）                 |
| 记忆不连贯         | L1 IndexedDB 未写入/被清       | 查 `appendTurn`/`recallTurns`；IndexedDB 版本升级逻辑                    |
| 召回结果不准        | bge-m3 未配 → 关键词回退         | 检查 `env.AI` binding；无则属预期降级                                      |
| Supabase 写入失败 | RLS / key 错误              | 查 `sbHeaders` 用 anon 还是 service_role；Worker 自动内存兜底不报错            |
| Vercel 构建失败   | Node runtime 错（须 Dynamic） | 确认 3 路由 `ƒ (Dynamic)`；`DEEPSEEK_API_KEY` 已配                      |
| Worker 部署失败   | 未 `--config` / secret 缺失  | `npx wrangler deploy --config apps/worker/wrangler.toml` + 配 Key |
| 前端缓存陈旧        | IndexedDB 存旧结果            | `loadResult` 命中即展示；清缓存或升 `db.ts` VERSION                         |
| 流式中断          | LLM 限流/网络                 | `streamSkill` try/catch 已回落 stub；查 Key 配额                        |

### NPM-01 · pnpm 在本机/CI/Cloudflare 均不可用

- **分类**：包管理器
- **触发场景**：执行 `pnpm install` / `pnpm run ...`（本机、GitHub Actions、Cloudflare 部署）
- **现象**：
  - 本机：`pnpm install` 报 `Done` / exit 0，但 `node_modules` 不建符号链接，`apps/web` 里 `next`/`react`/`zod` 全缺；`.npmrc` 的 `node-linker=hoisted` 被无视（`.modules.yaml` 恒为 isolated）。
  - CI/Cloudflare：装 workspace 内部包 `@ai-career-companion/*` 报 `404`，把 `*` 当成 registry 版本拉取。
- **根因（双根因）**：
  1. 本机 pnpm 11.15.1 **链接机制故障（环境级，不可配置修复）**，同机器 `/tmp` 副本复测 100% 复现。
  2. workspace 内部依赖用 `*` 写法 → npm 正常，但 **pnpm 当成 registry 版本拉取报 404**（与 `workspace:*` 协议互斥，无单一协议同时满足两者）。
- **解决方案**：**全仓库统一用 npm**；monorepo 用根 `package.json` 的 `workspaces` 字段，内部依赖保持 `*`，**禁用 pnpm**。
- **验证**：`npm install` 成功生成 `node_modules`；`npm run type-check` 0 报错；CI 的 npm job 全绿。
- **状态**：已规避（统一 npm 策略）
- **关联**：`MEMORY.md` 本地环境工具链 #40 / #42 / #43

### NPM-02 · 外部终端 `npm` 命令不识别

- **分类**：运行时 / 环境
- **触发场景**：在 IDEA 终端 / PowerShell / 系统 `cmd` 直接敲 `npm` / `npx`
- **现象**：`npm 不是内部或外部命令` / `command not found: npm`
- **根因**：本机**无系统级 Node**；Node/npm 仅存在于 WorkBuddy 托管目录 `C:\Users\asus-pc\.workbuddy\binaries\node\versions\22.22.2\`（含 `node.exe` / `npm.cmd` / `npx.cmd`）。
- **解决方案**：
  - 将该目录加入**用户/系统 PATH**（IDEA/PowerShell 重开即生效）；或调用 `npm.cmd` 全路径。
  - WorkBuddy 自带 git bash 已自动加此 PATH，仓库内 `node_modules` 已装好，配 PATH 后直接 `npm run dev` 即可。
- **验证**：新开终端执行 `npm -v` 正常输出版本号。
- **状态**：活跃（队友在 IDEA/PowerShell 常踩）
- **关联**：`MEMORY.md` 本地环境工具链 #46

### NPM-03 · turbo 报 `Could not resolve workspace`

- **分类**：构建工具
- **触发场景**：`npm run dev` / `npm run build`（经 `turbo` 编排）
- **现象**：`turbo` 报错 `Could not resolve workspace`
- **根因**：根 `package.json` 缺 `packageManager` 字段，`turbo`（2.10.5）靠它识别包管理器；缺失时回退逻辑失败。
- **解决方案**：根 `package.json` 保留唯一 `"packageManager": "npm@10.9.7"`（删 `devEngines` 块后必须补）。
- **验证**：`npm run dev` 正常启动 turbo 编排；`npm run type-check` 0 报错。
- **状态**：已修复（根已加 `packageManager`）
- **关联**：`MEMORY.md` 本地环境工具链 #47

### NPM-04 · `npm --workspace X dev` 语法错误

- **分类**：命令语法
- **触发场景**：只想启动/构建某个 workspace（如仅前端）
- **现象**：直接报错 `unknown command` 或忽略 `--workspace`
- **根因**：正确语法是 `npm run <script> --workspace <name>`，`npm --workspace X <script>` 顺序错误。
- **解决方案**：用根别名 `npm run web`（= `npm --workspace @ai-career-companion/web run dev`），或完整写法 `npm run dev --workspace @ai-career-companion/web`。避免 `wrangler dev`（需 Cloudflare 配置）。
- **验证**：`npm run web` 起前端于 `localhost:3000`；`npm run build --workspace @ai-career-companion/web` 构建通过。
- **状态**：活跃（已文档化，靠别名规避）
- **关联**：`MEMORY.md` 本地环境工具链 #47

### NPM-05 · Cloudflare Worker 部署 404

- **分类**：部署
- **触发场景**：Cloudflare 用 pnpm 部署 `apps/worker`
- **现象**：部署崩溃，找不到 `@ai-career-companion/llm` / `@ai-career-companion/types`
- **根因**：同 NPM-01(b) —— 内部依赖 `*` 写法与 pnpm `workspace:*` 协议冲突导致 404。
- **解决方案**：部署也用 `npm install`（**禁用 pnpm**）；`npx wrangler deploy --config apps/worker/wrangler.toml`（根目录 `/` 下 wrangler 找不到 toml，必须 `--config`）；Cloudflare 配 `DEEPSEEK_API_KEY` secret。
- **验证**：Worker 部署成功，`GET /health` 返回 200。
- **状态**：已规避（统一 npm）
- **关联**：`MEMORY.md` 部署配置 #56 / #66

### NPM-06 · `Invalid package manager specification`

- **分类**：配置
- **触发场景**：Cloudflare 解析 `devEngines.packageManager.version`
- **现象**：Cloudflare 报 `Invalid package manager specification (pnpm@^x.y.z)`
- **根因**：版本号带 caret `^`（如 `"^x.y.z"`），Cloudflare 解析器不接受范围写法。
- **解决方案**：去掉 caret，或**删除 `devEngines` 块**，改用顶层 `"packageManager": "npm@x.y.z"`（精确版本）。
- **验证**：Cloudflare 构建不再报该错；顶层 `packageManager` 为精确 `npm@10.9.7`。
- **状态**：已规避（删 devEngines，顶层 npm）
- **关联**：`MEMORY.md` 部署配置 #57

### NPM-07 · `ERR_PNPM_MINIMUM_RELEASE_AGE` 拒装

- **分类**：包管理器 / 供应链
- **触发场景**：pnpm 尝试安装发布 <1 天的 dev 依赖（如 `@typescript-eslint/*`、`postcss`、`prettier`）
- **现象**：`ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION` 拒绝安装
- **根因**：pnpm 11 供应链策略 `minimumReleaseAge` 默认拦截过新发布的包。
- **解决方案**：**不用 pnpm**；若强用需 `pnpm install --config.minimumReleaseAge=0`。
- **验证**：改用 npm 安装无此问题；CI 跑 npm job 全绿。
- **状态**：已规避（统一 npm）
- **关联**：`MEMORY.md` 本地环境工具链 #41

### NPM-08 · 双 lockfile 残留（pnpm-lock.yaml + package-lock.json）

- **分类**：配置 / 依赖
- **触发场景**：仓库根同时存在两份 lockfile
- **现象**：不同工具自动选其一，可能导致依赖树不一致、CI 与本地漂移。
- **根因**：历史双 PM 策略（计划书写 pnpm，本机实际用 npm）遗留。
- **解决方案**：`pnpm-lock.yaml` 已弃用可删除；CI / 部署只认 `package-lock.json`；全仓库统一 npm。
- **验证**：根目录仅 `package-lock.json`；`npm ci` 可复现安装。
- **状态**：已规避（CI 已改 npm，lockfile 待清理）
- **关联**：`MEMORY.md` 本地环境工具链 #44 / #66

### NPM-09 · 根 `package.json` 重复 `packageManager` 键

- **分类**：配置
- **触发场景**：根 `package.json` 同时存在 `packageManager: npm@...` 与 `packageManager: yarn@...`
- **现象**：JSON 解析取最后一个 → 实际变为 `yarn`；CI 中 turbo 去找 yarn 而 Runner 无 yarn → 构建崩。
- **根因**：历史残留的 yarn 行未清理，与 npm 行形成重复 key。
- **解决方案**：删除 yarn 行，唯一保留 `"packageManager": "npm@10.9.7"`（2026-08-14 已修）。
- **验证**：`node -e "console.log(require('./package.json').packageManager)"` 输出 `npm@10.9.7`；JSON 合法无重复键。
- **状态**：已修复（2026-08-14）
- **关联**：`2026-08-14` 工作日志

## 11. 日常工作流（全角色）

> 本节点是「人 / AI 每日怎么协作」的操作手册，配合 `ROADMAP.md`（迭代循环）与 `TASKBOARD.md`（看板）使用。AI 启动时会自动读本章（见 §0）。

### 11.1 每日启动（AI 自动，人无需手动读）

| 步骤 | 动作 |
| -- | -- |
| 1 | AI 读 `docs/项目说明.md`（本文件，全局约束） |
| 2 | AI 读 `docs/ROADMAP.md`（当前迭代循环 + backlog 优先级） |
| 3 | AI 读 `docs/TASKBOARD.md`（认领 / 移动卡片，需求溯源） |
| 4 | 用 `Grep` / `Read` 定位具体源码（不整仓扫） |
| 5 | 改完跑 `npm run type-check` → 更新看板卡片 → 提示用户提交 |

> AI 不主动 `git commit` / `git push`、不启动 dev server、不登录任何云端后台（见 §9、§10）。

### 11.2 需求 → 验收闭环

```
需求(Issue 模板) → 队长派发(看板待办) → 成员认领(进行中 + 开功能分支)
   → 开发(npm run type-check 0 报错) → 提 PR(标题含 Closes #编号)
   → 合入 基础骨架(GitHub Projects 自动移「待审核」)
   → 队长功能验收(本机 npm run web 自测) → 卡移「完成」+ Issue close
   → 回到 ROADMAP 下一迭代循环
```

### 11.3 角色动作

**队长（A，统筹 / 基础设施 / 部署）**

1. 读全局（AI 自动完成，无需手动）
2. 需求入口：把「谁在哪次对话提的需求」建成 Issue（用 `.github/ISSUE_TEMPLATE`，强制填需求来源 / 优先级 / 验收标准）→ 自动进 Projects 待办
3. 派发：在 `TASKBOARD.md` 待办列建卡或移动，指定负责人（参照 §7 分工表）
4. 定里程碑：按 `ROADMAP.md` 迭代环决定下一个要赢的里程碑
5. 评审 PR：遵循 §9 分支纪律「短生命周期功能分支 → PR → 评审 → 合 `基础骨架`」
6. 验收：「待审核」卡片由队长 / 评委验收 → 移「完成」
7. 治理硬任务：改默认分支为 `基础骨架`、确保 CI 跑 `基础骨架`（不做则队友仍以为停滞）

**成员（B 前端 / C 后端AI / D 数据测试）**

1. 领任务：在 Projects 或 `TASKBOARD.md` 待办列认领一张卡
2. 移到进行中：把卡剪到「进行中」列，填负责人 + 分支
3. 开功能分支：从 `基础骨架` 切短生命周期分支，不直接在活跃分支改
4. 编码：先读 `项目说明.md` §3 定位源码；守住三条降级链、不破坏 `packages/types` 契约
5. 自检：跑 `npm run type-check` 须 0 报错（见 §8 标准）
6. 提 PR：push 分支 → 开 PR，描述写 `Closes #编号` 关联 Issue；合入 `基础骨架` 后把卡移到「待审核」

### 11.4 看板移卡规则

1. **待办 → 进行中**：成员认领时移动，填负责人 + 功能分支名
2. **进行中 → 待审核**：提 PR 并 `Closes #` 合入 `基础骨架` 后移动（或靠 GitHub Projects 内置自动化）
3. **待审核 → 完成**：队长 / 评委功能验收通过后移动，并 close 对应 Issue
4. **每次移卡必须 `git commit` 进 `基础骨架`**：队友 `pull` 即同步；markdown 看板是 AI 无关的真相源，任何 AI（WorkBuddy / Trae / dumate / Claude）和队友均直接读写

### 11.5 队友如何提需求 / 提问

- **提任务 / Bug**：GitHub 仓库 `Issues` → `New issue` → 选模板（功能 / 任务 或 Bug 反馈）→ 填字段（优先级 / 预估工作量 / 功能描述 / 验收标准 / **需求来源**）→ 提交后自动进 Projects「待办」
- **纯提问（非任务）**：建议在仓库开 **Discussions**（Settings → Features → 勾 Discussions），Issue 只收任务 / Bug，避免噪音
- **换 AI 工具**：Trae / dumate / ChatGPT 等只需一句「先读 `docs/项目说明.md` 当上下文」即可拿到同等全局信息（真相源是 markdown，不锁死 WorkBuddy）

### 1. 项目背景与定位

#### 1.1 项目概述

AI学职同伴是面向**双非院校学生**的轻量化 AI 学职成长助手，以 WebApp 形式交付，
评委通过线上 URL 直接访问体验。

#### 1.2 定位定义（本版修订）

> **面向双非学生的「信息差填平」平台**——主动聚合学校、企业的权威公开信息，
> 以卡片化界面降低认知负荷；AI 助手作为第二层能力，将信息转化为个人可执行的行动方案。

#### 1.3 功能主次关系

| 层级 | 功能域 | 定位 | 说明 |
|---|---|---|---|
| **第一层** | **信息中枢** | 核心 | 主动/按需提供准确的岗位、学习、政策信息。用户打开产品的首要理由 |
| 第二层 | **AI 学职助手** | 重要 | 五 Skill（诊断/规划/练兵/信息差/包装），将信息转为行动 |
| 第三层 | **成长体系** | 留存 | 打卡、积分、画像；简历能力并入「成果包装」 |
| 第四层 | **数据看板** | 观测 | 成长轨迹、能力增长、面试成功率等量化呈现 |

**修订理由**：目标用户的首要痛点是"不知道有什么机会"。提供准确信息比陪伴式对话更直接地解决该痛点。
同时，五个 Skill 在代码层面高度同质（同一对话引擎的不同提示词），宜收拢为统一专区。

#### 1.4 与原始方案的关系

参赛方案 v3.6 是本项目的需求基线。本版在其基础上做了三项调整：

| 方案 v3.6 原设定 | 本版调整 | 原因 |
|---|---|---|
| 五 Skill 为产品核心 | 降为第二层，收进统一专区 | 功能同质，且信息获取才是壁垒 |
| 学职频道自建社区 | 改为依托微信/QQ/学校 APP 等既有渠道 | 自建社区冷启动成本高，评委体验周期内难见效 |
| 简历为独立模块 | 并入「成果包装」Skill | 二者同属"成果表达"场景，拆分增加认知负担 |

### 4. 信息获取机制（核心设计）

"主动提供准确信息"由三层能力共同实现，各层解决不同问题，缺一不可。

```
① 精选资源库（Curation）   → 解决「准确性」
   人工把关的权威来源：高校就业网、企业校招官网、学习平台
   仅存储标题、摘要、跳转链接、标签，不存储正文内容

② AI 联网检索（Live Search） → 解决「实时性」
   用户提问或定时触发 → 调用搜索 API → 结果结构化
   以「来源卡片」形式呈现：标题 + 链接 + 摘要 + 来源站点

③ 用户众包贡献（UGC）      → 解决「长尾信息与社区感」
   用户提交双非友好岗位、内推信息、面经
   提交 → 审核队列 → 入库 → 贡献者获得积分奖励
```

#### 4.1 三层的互补关系

| 层 | 核心价值 | 单独使用的局限 |
|---|---|---|
| 资源库 | 信息经过人工筛选，准确可信 | 依赖人工维护，无法保证实时性 |
| 联网检索 | 覆盖广、可获取最新信息 | 结果质量参差，且**无法检索到隐性信息** |
| UGC 众包 | 覆盖搜索引擎无法索引的长尾信息 | 依赖社区活跃度，存在冷启动问题 |

> **关键判断**：诸如"某企业不限制第一学历"这类信息，公开搜索引擎无法索引，
> 通用 AI 工具亦无法回答。此类信息只能通过用户众包获取，
> 这是本项目区别于通用 AI 工具的关键壁垒，也是"双非垂直定位"由口号转为数据资产的路径。

#### 4.2 联网检索技术选型

| 方案 | 接入方式 | 优势 | 约束 |
|---|---|---|---|
| **方案 A：DeepSeek 内置联网** | Chat API 传 `web_search_options.enable=true`；或 Responses API 声明 `tools:[{type:"web_search"}]` | 零新增依赖，改动量最小 | 需在平台领取联网搜索资源包；QPS 限制 5；服务地域为广州 |
| **方案 B：博查搜索 API** | `POST https://api.bochaai.com/v1/web-search`，Header 携带 Bearer Key | **DeepSeek 官方联网搜索供应商**；国内合规、数据不出海；平均响应 0.15 秒；**支持 `include` 参数限定搜索域名**；提供免费额度 | 需注册账号获取 API Key |

**博查 `include` 参数为本方案关键能力**，可将检索范围限定在目标学校与企业官网域名内，避免结果发散：

```json
{
  "query": "2027 校园招聘 软件工程 本科",
  "include": "join.qq.com|edu.cn|zhaopin.com",
  "freshness": "oneMonth",
  "summary": true,
  "count": 10
}
```

返回字段包含 `name`、`url`、`snippet`、`summary`、`siteName`、`siteIcon`、`datePublished`，
可直接渲染为来源卡片，无需额外数据加工。

**选型建议**：优先采用方案 A 验证效果（零成本），若结果质量或域名限定能力不足，再接入方案 B。

#### 4.3 合规红线

1. **仅存储链接与摘要，不抓取、不存储正文内容**。跳转链接属于合规引用，全文抓取不属于。
2. 联网检索结果**必须标注来源站点与发布时间**，保证用户可核验。
3. UGC 内容**必须经过审核队列**方可公开展示。
4. 不采集与服务无关的个人信息；用户画像存储遵循最小必要原则。

### 5. 界面与交互规范

采用**微软 Copilot 官方 UX 规范**作为卡片化设计依据。该规范经实测验证：
Word 使用率提升 27%、PowerPoint 提升 43%、加载耗时降低 50% 以上。

| 原则 | 具体约束 |
|---|---|
| 内联卡片（Inline Widget） | 单卡片内**操作按钮不超过 2 个**；内容须在一屏内完整呈现；**禁止卡片内滚动、分页、标签页、筛选器** |
| 渐进披露 | 默认呈现最简结果，用户需要更多细节时再逐层展开 |
| 提取能力而非复制界面 | 不将完整页面塞入对话流，仅暴露高价值的原子能力 |
| 上下文保持 | 切换卡片或视图时不丢失对话语境 |
| 状态显式化 | 加载、禁用、成功、失败（含恢复入口）四种状态均需界面表达，不能仅依赖模型文本描述 |

**对现有五 Skill 的改造要求**：当前输出为长文本，应调整为
「摘要卡片 + 最多 2 个行动按钮 + 展开查看全文」的结构。

### 1. 目标架构

#### 1.1 功能架构

```
用户（双非学生）
  │
  ├── 专区 A：AI 学职助手 ──── 五 Skill（Tab 切换，卡片化输出）
  │        └── 成果包装内集成「简历数据」
  │
  ├── 专区 B：信息中枢（核心）──┬─ 精选资源库（仅存链接与摘要）
  │        └── 三栏式岗位浏览 ──┼─ AI 联网检索（限定域名）
  │                             └─ 用户贡献（审核后入库）
  │
  ├── 专区 C：我的成长 ──── 打卡 / 积分 / 画像（留存体系）
  │
  ├── 专区 D：数据看板 ──── 成长轨迹 / 能力增长 / 面试成功率
  │
  └── 基础入口 ──── 帮助 / 设置 / 账号登录（须完整保留）
```

#### 1.2 导航结构

##### 推荐命名方案（两字，整齐且干练）

```
[AI学职同伴]   助手   岗位   成长   看板          帮助  设置  [账号]
   左侧 logo   ←──── 四专区入口 ────→        ←── 基础入口 ──→
```

| 专区 | 推荐命名 | 覆盖内容 |
|---|---|---|
| A | **助手** | 五个 Skill（诊断/规划/练兵/信息差/包装） |
| B | **岗位** | 信息中枢：岗位浏览、联网检索、资源库、用户贡献 |
| C | **成长** | 打卡、积分、画像 |
| D | **看板** | 数据看板 |

##### 备选命名方案

| 方案 | A | B | C | D | 特点 |
|---|---|---|---|---|---|
| 方案 B（动宾式） | 问 AI | 找岗位 | 看成长 | 看数据 | 动作导向，最易理解，略长 |
| 方案 C（完整式） | 学职助手 | 岗位机会 | 我的成长 | 数据看板 | 辨识度最高，但占位长 |

> **选型建议**：推荐两字方案。理由：与 logo 相邻时语义自明；四项等宽，视觉整齐；
> 为右侧基础入口（帮助/设置/账号）预留充足空间，避免导航换行。
> 最终命名由组长 A 组织确认后统一替换。

##### 导航约束（硬性）

1. **帮助、设置、账号登录三项必须保留在一级导航**，不得移除、合并或深埋至二级。
   理由：属于用户预期中的基础入口，缺失会显著降低评委对产品完成度的评价。
2. 导航**须单行显示**。若项数过多导致换行，优先压缩间距与图标，而非删减功能。
3. 未登录状态显示"登录"，已登录状态显示账号标识。

## 信息库 / 知识库与学职频道实施线路（路线图）

> 本节由 2026-09-03 架构讨论沉淀：把 W1 D5（联网检索来源卡片）、UC-B4（资源库）、UC-B5（用户贡献）与后续「知识库体系 / 学职频道 / 管理员后台」捋成一条端到端技术线。本期（MVP W1/W2）只落前端骨架，后端与多角色依赖后续 cycle。
> 设计原则：严格遵循 §5 微软 Copilot UX 规范（内联卡片≤2 按钮、渐进披露、状态显式、上下文保持）与 §4.3 合规红线（仅存链接摘要、UGC 必过审核）。

### 一、身份 / 角色制度（产品内权限）

与开发团队角色（A/B/C/D）无关，是产品内权限。账号体系由 Supabase Auth 承载（本期未建，先用**测试账号 + localStorage 角色**模拟）。

| 角色 | 核心权限 |
|---|---|
| 学生（普通用户） | 浏览所有 public 资源库/笔记；创建并编辑**自己的**资源库与笔记；提交贡献（待审核）；用智能体问答（系统库+自有库） |
| 高校老师 / 就业指导教师 | 编辑/审核**系统资源库**（受保护）；审核学生贡献；查看学生进展（v3.6 高校版，缓） |
| 系统维护员（管理员） | 平台运维、审核队列、用户管理、检索 Key 配置、数据备份 |

权限矩阵（RACI 简表）：编辑系统资源库 / 审核贡献 仅「高校老师 + 系统维护员」；配置 Key/后台 仅系统维护员。系统资源库（集成岗位信息+精选网站）**受保护**，修改需特殊身份。

### 二、信息库数据模型（统一 InfoItem）

所有信息用同一结构，靠维度区分：

- `kind`：岗位链接 / 学校信息（官网·教务处·财务处·比赛）/ 学习资源 / 政策 / 笔记
- `visibility`：`public`（审核后公开）/ `private`（仅自己，笔记）
- `status`：已发布 / 待审核 / 驳回
- 字段：`title / summary / url / tags / sourceSite / category / ownerId / ownerRole`
- **红线**：仅存链接与摘要，不抓正文。
- 多库模型：1 个 `system` 库（受保护，特殊身份可改）+ N 个 `user` 库（学生自建，辅助）。

### 三、资源库调用（智能体问答知识库）技术线

前端「知识库选择器」→ `POST /api/kb-query`（Worker）→ bge-m3 向量化 → pgvector 语义检索（**依赖 B-1~B-4 修复：WORKER_URL 改域名、调用接入、向量生成、检索方式**）→ 答案以**内联来源卡片/引用卡片**呈现（Copilot 规范）。
⚠️ 阻塞：当前语义检索链路未接通，本期 KB 问答**不做真实检索**，仅留 UI 骨架与占位接口。

### 四、知识库大体系（未来 cycle）

- 文件导入：doc / ppt / pdf / png·jpg 等多格式 → 解析 + 分块 + 向量化入库（复用 bge-m3）。
- 资源库作为「特殊默认知识库」存在，用户可直接增删改查其中内容。
- 智能体可直接询问知识库相关问题（复用 `useSkill` 统一引擎 + `SkillCardView`）。

### 五、学职频道（未来 cycle，MoSCoW = Could）

渠道：微信小程序 / QQ 频道 / 微信公众号 / 学校官方 APP + 平台自建频道（多方信息同步，做不到实时则每日一次）；功能：发布帖子、评论求助、与官方直接沟通（反馈渠道）。本期仅保留引导入口，不构建。

### 六、管理员后台（未来 cycle）

高校老师 / 系统维护员：审核队列（贡献→发布）、进度协调、项目管理与优化、检索 Key 配置。本期仅设计权限模型，不做后台 UI。

### 七、本期（MVP）前端落地范围
